# BrickSmart

BrickSmart is a model-agnostic, catalog-driven system that turns segmented 3D
models into inventory-aware physical builds.

The system supports the workflow from model intake and semantic review through
contract registration, structural and functional planning, validation, and
interactive build instructions.

BrickSmart is organized around two main application layers:

- a user-facing workflow for model submission, segment review, teacher
  confirmation, inventory selection, build submission, and result presentation;
- a deterministic planning runtime that consumes confirmed model contracts,
  the shared block catalog, and run-level inventory.

The user-facing workflow is under active development and may evolve
independently of the planning runtime. Its framework, page structure, and
interaction design are not treated as fixed architectural requirements.

The stable integration boundary is the versioned model contract and the
validated build API. Frontend implementations produce or update confirmed
contract artifacts, while the planning runtime consumes those artifacts
deterministically.

The repository separates authoritative model data, versioned model contracts, generated run outputs, and immutable regression fixtures:

```text
model_store/       immutable OBJ content addressed by SHA-256
model_registry/    versioned task contexts and teacher-confirmation artifacts
runs/              dynamically generated production and local executions
tests/regression/  compact reviewed source-repository fixtures
```

The `backend/` directory contains the Python planning and service implementation;
it is one part of the BrickSmart system rather than the definition of the whole
product. The `frontend/`, model and contract stores, runtime services, validation
layers, and generated build players together form the complete application.

## Core design rules

1. `block_catalog/block_definitions.xlsx` is the single source of truth for block geometry, connector faces, permitted rotations, priorities, colors, and functional metadata.
2. Block geometry or connector rules must not be duplicated in Python, JSON, YAML, or a generated CSV catalog.
3. Inventory quantities are run-level configuration and remain separate under `config/inventory/`.
4. Every build uses a confirmed, versioned model contract.
5. Production runs are generated under `runs/`; regression baselines belong under `tests/regression/`.
6. `pipeline_runtime/` is a temporary engine workspace and contains no authoritative model, contract, or result data.

## Requirements

Install the following before running the project:

- Python 3.11 or a compatible version declared by `pyproject.toml`;
- `pip`;
- GNU Make for the convenience commands in the `Makefile`;
- Git.

A local LLM is not used during a validated build. LLMs may optionally assist the frontend or contract-authoring workflow before teacher review; only reviewed decisions stored in the immutable contract are consumed by the validated runtime.

## Block catalog and inventory

### Block catalog

The application loads this workbook directly:

```text
block_catalog/block_definitions.xlsx
```

It is authoritative for:

- block identifiers and dimensions;
- visible and reserved geometry;
- connector-face definitions;
- male and female face compatibility;
- allowed rotations;
- packing priorities;
- colors and visualization metadata;
- functional roles and related block metadata.

Do not create or maintain a replacement CSV catalog. Do not hard-code workbook values in planner code.

### Inventory

Inventory configuration contains available quantities only. It must not redefine block geometry, rotations, connector faces, priorities, colors, or functional behavior.

Example:

```yaml
inventory:
  rotation_block: 2
  hinge_block: 2
  big_wheel: 4
  small_wheel: 4
  standard_2x2x2: 16
  standard_2x3x2: 10
  standard_2x4x2: 12
```

Inventory keys must match block identifiers in `block_definitions.xlsx`. The committed `config/inventory/standard_kit.yaml` file is the authoritative example for the schema supported by the current code.

Each build receives an inventory file explicitly:

```bash
bricksmart-build \
  --contract contract://classroom-model-standard-kit \
  --inventory config/inventory/standard_kit.yaml
```

The planner records inventory usage and the final recount in the run artifacts.

The planner first generates mechanically valid segment alternatives without
committing inventory. It then reserves required functional components,
deduplicates declarations that refer to the same physical component, evaluates
whole-model demand, commits a complete allocation atomically, and independently
recounts final parts. Detailed behavior is documented in
[STRUCTURAL_PLANNER.md](docs/STRUCTURAL_PLANNER.md).

## Model and contract lifecycle

BrickSmart separates model geometry from model interpretation.

### Model geometry

An OBJ is imported once into the immutable model store. Model bytes are addressed by SHA-256 and referenced through a stable URI:

```text
model://<model-id>
```

### Model contract

A contract describes how BrickSmart should interpret and build a specific segmented model. It contains:

- the model reference and checksum;
- source-segment identities;
- confirmed segment names and semantic roles;
- symmetry and pairing information;
- interface expectations;
- functional attachment intent;
- build constraints and teacher-confirmed overrides.

All models use the same contract schema, but each contract contains model-specific values.

### Contract artifacts

```text
task_context.json
segment_confirmations.csv
manifest.json
```

Typical ownership:

| Artifact | Produced or updated by | Purpose |
|---|---|---|
| `task_context.json` | User-facing workflow | Model reference, build intent, constraints, and semantic context |
| `segment_confirmations.csv` | Teacher-confirmation workflow | Confirmed or corrected segment meanings |
| `manifest.json` | Contract registry | Revision lineage, checksums, and immutable metadata |
| `run.json` | Build service | Execution lineage, status, inputs, and output references |

The validated planning runtime consumes the confirmed contract. Temporary files named like `simulated_teacher_segment_confirmations_*.csv` are development stand-ins only and must not be used as final production contract artifacts.

## Adding a new model

A new object category uses the same runtime, contract schema, catalog, and
inventory interfaces as every existing model. It must not be added to a Python
enum, model-profile switch, planner dictionary, API branch, or separate player.

1. Import the OBJ through `POST /api/models/upload` or
   `bricksmart-model-store import`.
2. Save the returned `model://<model-id>` URI and SHA-256.
3. Create `task_context.json` from
   `examples/contracts/model_contract_template.json`.
4. Generate the frontend or teacher-reviewed segment-confirmation artifact.
5. Set the model source, coordinate transforms, preprocessing, segment
   semantics, symmetry, interfaces, structural intent, and reusable functional
   capability declarations.
6. Register an immutable contract revision.
7. Run the generic build endpoint or `bricksmart-build`.
8. Review inventory, connectivity, symmetry, contact, build-order, and final
   claim artifacts.
9. Add a reviewed regression fixture only when the model is intended to become
   a maintained reference baseline.

A Python change is appropriate only for a genuinely new reusable physical
capability, not for a new model name or object category.

## User-facing workflow

BrickSmart includes a user-facing workflow for:

- submitting or selecting a segmented 3D model;
- reviewing proposed segment meanings;
- recording teacher-confirmed semantics and build intent;
- selecting an inventory configuration;
- starting a build;
- reviewing validation results;
- opening interactive build instructions.

The current user interface is evolving. Its implementation framework, page
structure, and visual design may change as the project develops.

The frontend is expected to remain separate from the validated planning logic.
It may assist with model intake, semantic proposals, teacher review, contract
authoring, and result presentation, but it does not define block geometry,
connector rules, inventory policy, or final physical validation.

The stable frontend-to-runtime handoff consists of:

```text
confirmed model contract
teacher-confirmation artifact
model URI and checksum
inventory profile
build request
```

The validated planning runtime returns run metadata, validation results,
structured build artifacts, and `build_instructions.html`. This boundary allows
the project to adopt or replace frontend technologies without changing the
catalog-driven planning engine.

## Deterministic validated builds

BrickSmart uses LLMs only as optional **contract-authoring assistants**. A
validated build never calls an LLM. The reviewed model contract already
contains confirmed segment meanings, interface intent, functional capability
declarations, and catalog queries.

```json
{
  "execution_policy": {
    "mode": "validated",
    "allow_runtime_llm": false,
    "final_claim_requires_deterministic_inputs": true
  },
  "llm": {
    "llm2": {
      "enabled": false,
      "role": "contract_authoring_only"
    }
  }
}
```

The same contract revision, model checksum, workbook, and inventory therefore
produce the same planner inputs. `exploratory` mode may permit runtime LLM
enrichment, but its result is marked provisional and cannot receive a validated
final claim.

## CLI workflow

### 1. Import model geometry

```bash
bricksmart-model-store import ./model.obj \
  --model-id classroom-model
```

Expected result:

```text
model://classroom-model
```

The store writes the model once, records its checksum, and returns a stable URI. Re-importing identical content must not create conflicting authoritative copies.

### 2. Prepare and confirm the contract

The current user-facing or contract-authoring workflow creates:

```text
task_context.json
segment_confirmations.csv
```

The teacher reviews or corrects the proposed segment meanings before the contract is registered.

### 3. Register an immutable contract revision

```bash
bricksmart-contract-registry import ./task_context.json \
  --confirmations ./segment_confirmations.csv \
  --contract-id classroom-model-standard-kit
```

Expected versioned reference:

```text
contract://classroom-model-standard-kit@<revision-id>
```

The unversioned URI resolves to the current revision:

```text
contract://classroom-model-standard-kit
```

A registered revision is immutable. A later teacher correction creates a new revision rather than overwriting the prior one.

### 4. Build

```bash
bricksmart-build \
  --contract contract://classroom-model-standard-kit \
  --inventory config/inventory/standard_kit.yaml
```

Optional explicit run identifier:

```bash
bricksmart-build \
  --contract contract://classroom-model-standard-kit \
  --inventory config/inventory/standard_kit.yaml \
  --run-id classroom-model-demo
```

Every execution creates a new isolated run:

```text
runs/<run-id>/
├── run.json
├── inputs/
├── logs/
└── artifacts/
```

Do not reuse a production run directory unless the command explicitly supports and requests a clean rebuild.

## Run structure and artifacts


### Output-path ownership

A model contract cannot select its output directory. The run store assigns every
execution an isolated directory under the configured runs root.

Historical `paths.output_dir` values are removed when contracts are registered
and are ignored by the runner. This prevents a model-specific contract from
writing outside the run store or overwriting another execution.

### HTML generation provenance

`build_instructions.html` is generated by
`backend/bricksmart/reporting/true_build_player.py` after the planner produces a
validated final result. The player consumes repository-generated CSV and JSON
run artifacts plus catalog-derived display metadata. It is a self-contained
HTML file and does not load external project files when opened.

The reviewed documentation copy at
`docs/examples/bird_build_instructions.html` is a stable example generated from
the same repository code. New executions still write their own HTML under the
run directory.

### `run.json`

`run.json` records the execution lineage and status, including:

- run identifier;
- model URI and checksum;
- contract URI and revision;
- inventory configuration;
- timestamps;
- planner and schema versions;
- validation status;
- artifact references.

### `inputs/`

The `inputs/` directory snapshots the exact contract, teacher confirmations, inventory, and other run-level configuration used for the build.

Model bytes are normally referenced by immutable URI and checksum rather than copied into every run.

### `logs/`

The `logs/` directory contains diagnostic and execution logs. Logs are supporting records and are not authoritative build outputs.

### `artifacts/`

The exact artifact set may vary by planner path, but it includes generated planning, validation, instruction, and visualization outputs such as:

- final parts and block counts;
- per-segment subassemblies;
- parts ordered by build step;
- module and final assembly instructions;
- classified interfaces and connector decisions;
- connector, contact, collision, and orientation audits;
- inventory usage and final recount;
- symmetry and connectivity validation;
- final build claims and validation summaries;
- interactive build-step players;
- final-state visualizations.

Common artifact filenames may include:

```text
final_parts.csv
parts_by_step.csv
build_instructions.json
build_instructions.html
classified_interfaces.csv
inventory_usage.json
final_build_claim_summary.json
final_block_contact_audit_build_graph_summary.json
visualizations/proper_complete_build_steps.html  # legacy compatibility path
```

`build_instructions.html` is the canonical human-readable build guide. For a
validated row/column build it is a self-contained interactive 3D step player.
The legacy `visualizations/proper_complete_build_steps.html` file is retained
with identical content for compatibility. User-facing HTML uses `Block types` and `Block type` terminology; it does not expose workbook implementation details. Unlimited reference builds are visibly labeled as such. Simpler constrained-planning runs
produce a portable tabular HTML guide from the same data written to
`build_instructions.json`.

Treat the run manifest and validation summaries as the primary entry points when reviewing a completed execution.

## Testing

### Unit and integration tests

Python runtime and service tests belong under:

```text
backend/tests/
```

Run them with:

```bash
pytest -q backend/tests
```

### Regression baselines

Regression baselines belong under:

```text
tests/regression/bird/
tests/regression/airplane_reference_unlimited/
tests/regression/airplane_standard_kit/
```

They are compact source-repository fixtures, not production runs. The airplane reference is explicitly unlimited; the standard-kit airplane fixture expects a structured inventory-infeasibility result.

The regression suite may compare:

- total and per-family block counts;
- placements and rotations;
- source-segment assignments;
- subassembly and assembly ordering;
- inventory usage and recount;
- symmetry and connectivity;
- required artifact presence;
- final validation claims.

Run baseline comparisons:

```bash
make regression
```

Run live end-to-end checks into `.test-runs/`:

```bash
make regression-bird
make regression-airplane-reference
make regression-airplane-standard-kit
```

When planner behavior is intentionally changed, review the generated differences before updating a baseline. Never replace a baseline solely to make a failing test pass.

By default, local development uses the repository-level storage directories:

```text
model_store/
model_registry/
runs/
```

Production roots may be overridden:

```bash
export BRICKSMART_MODEL_STORE_ROOT=/data/bricksmart/model_store
```

## Troubleshooting

### `bricksmart-build: command not found`

Activate the virtual environment and reinstall the BrickSmart Python package:

```bash
source .venv/bin/activate
python -m pip install -e ".[dev]"
```

On Windows:

```powershell
.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
```

### Workbook not found

Run commands from the repository root and verify:

```bash
ls block_catalog/block_definitions.xlsx
```

Do not substitute a generated CSV catalog.

### Inventory contains an unknown block ID

Ensure every inventory key exactly matches a block identifier in `block_definitions.xlsx`. Inventory configuration may specify quantities only for catalog-defined blocks.

### Contract cannot resolve its model

Confirm that the model URI exists in `model_store/`, that the checksum matches, and that the contract points to the intended model revision.

### Build stops before planning

Review:

```text
runs/<run-id>/run.json
runs/<run-id>/logs/
runs/<run-id>/inputs/
```

Typical causes include an invalid contract, missing teacher confirmations, unknown inventory identifiers, checksum mismatch, or schema-validation failure.

### Build completes but validation fails

Start with the final validation and claim summaries under:

```text
runs/<run-id>/artifacts/
```

Then inspect the related inventory, connectivity, symmetry, collision, connector-contact, and assembly-order audits.

### Regression output changed

Determine whether the change is:

1. an unintended behavioral regression;
2. a deliberate planner improvement;
3. a fixture or schema migration.

Only reviewed deliberate changes should update files under `tests/regression/`. Full diagnostics, arrays, LLM traces, and generated HTML remain under `.test-runs/` and are not committed.

## Development expectations

- Keep the planner model-agnostic.
- Read block definitions from the XLSX workbook.
- Keep inventory separate from catalog metadata.
- Preserve source-segment lineage throughout planning.
- Validate inventory, collisions, connector compatibility, connectivity, symmetry, and assembly order before making a final build claim.
- Add unit or integration tests for behavior changes.
- Add or update regression baselines only after explicit review.
- Keep generated run data out of production source directories.
